Lab 3 Questions and Answers
============================

Question 1: What is the purpose of having an individual handler function for each exception/interrupt? (i.e., if all exceptions/interrupts were delivered to the same handler, what feature that exists in the current implementation could not be provided?)

Answer: Having individual handler functions for each exception/interrupt allows each handler to push its specific trap number onto the stack before jumping to the common _alltraps function. This trap number is crucial for the kernel to distinguish between different types of exceptions and handle them appropriately. For example:
- Page faults (trap 14) need different handling than divide-by-zero errors (trap 0)
- System calls (trap 48) need different handling than breakpoints (trap 3)
- Some exceptions have error codes, others don't

If all exceptions went to the same handler, we would lose the ability to identify which specific exception occurred, making it impossible to implement proper exception-specific handling in trap_dispatch().

Question 2: Did you have to do anything to make the user/softint program behave correctly? The grade script expects it to produce a general protection fault (trap 13), but softint's code says int $14. Why should this produce interrupt vector 13? What happens if the kernel actually allows softint's int $14 instruction to invoke the kernel's page fault handler (which is interrupt vector 14)?

Answer: No special code was needed to make user/softint behave correctly. The program issues "int $14" (page fault interrupt) from user mode (DPL=3), but the IDT entry for interrupt 14 has DPL=0 (kernel privilege level only). When a user program tries to invoke an interrupt with insufficient privileges, the x86 processor automatically generates a general protection fault (interrupt vector 13) instead.

This is a security feature - if the kernel allowed user programs to directly invoke the page fault handler, it would be a major security vulnerability. Malicious user programs could potentially:
- Manipulate the kernel's page fault handling mechanism
- Cause the kernel to access arbitrary memory addresses
- Bypass normal memory protection mechanisms
- Potentially crash or compromise the kernel

Question 3: The break point test case will either generate a break point exception or a general protection fault depending on how you initialized the break point entry in the IDT (i.e., your call to SETGATE from trap_init). Why? How do you need to set it up in order to get the breakpoint exception to work as specified above and what incorrect setup would cause it to trigger a general protection fault?

Answer: The breakpoint exception behavior depends on the DPL (Descriptor Privilege Level) field in the IDT entry:

Correct setup (generates breakpoint exception):
- SETGATE(idt[T_BRKPT], 0, GD_KT, t_brkpt, 3);
- DPL = 3 allows user-mode programs to invoke the breakpoint handler

Incorrect setup (generates general protection fault):
- SETGATE(idt[T_BRKPT], 0, GD_KT, t_brkpt, 0);
- DPL = 0 restricts access to kernel mode only

When DPL = 0, user programs cannot directly invoke the breakpoint interrupt, so the processor generates a general protection fault instead. The breakpoint exception is special because it's designed to be invokable from user code for debugging purposes.

Question 4: What do you think is the point of these mechanisms, particularly in light of what the user/softint test program does?

Answer: These privilege level mechanisms provide crucial security and protection:

1. **Selective Access Control**: The kernel can choose which interrupts user programs are allowed to invoke directly (like breakpoints for debugging) while protecting critical system interrupts (like page faults).

2. **Security Boundary Enforcement**: Prevents user programs from directly invoking kernel-level exception handlers, which could be used to bypass security checks or manipulate kernel state.

3. **System Integrity**: Ensures that only the kernel can handle certain types of exceptions that require elevated privileges or access to system resources.

The user/softint test demonstrates this protection - it tries to invoke a page fault handler directly, which should fail with a general protection fault, proving that the privilege level checking is working correctly.

Question 5: In Exercise 9, when running backtrace from the kernel monitor after running user/breakpoint, what causes the page fault that occurs when the backtrace traverses into lib/libmain.c?

Answer: The page fault occurs because the kernel's debuginfo_eip() function tries to access user-space debugging symbols (stabs and stabstr) when generating the backtrace for user code. 

When the backtrace reaches user code (lib/libmain.c), debuginfo_eip() attempts to read the user program's symbol table to provide meaningful function names and line numbers. However, the user_mem_check() calls we added to debuginfo_eip() validate this memory access. If the user memory containing the debug symbols is not properly mapped, not accessible with the required permissions, or the memory layout doesn't match what the kernel expects, the user_mem_check() calls detect this as invalid memory access.

This is actually correct behavior - the kernel should not access invalid or improperly mapped user memory, even for debugging purposes. The page fault demonstrates that our memory protection mechanisms are working correctly by preventing the kernel from accessing potentially invalid user memory addresses.
